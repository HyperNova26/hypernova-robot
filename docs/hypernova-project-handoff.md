# HyperNova 프로젝트 인수인계 문서

이 문서는 이전 대화나 모집글 원본 없이도 다른 프로젝트, 팀 또는 에이전트가
HyperNova의 기획과 현재 상태를 이어받을 수 있도록 만든 독립형 기준 문서다.

기준 시점은 **2026년 8월 14일 KST**다. 시점에 따라 바뀔 수 있는 인원, 역할,
예산, 장비 대여, 대회 일정은 외부에 재사용하기 전에 다시 확인한다.

이 문서에는 내부 역할과 재무 현황이 포함된다. 공개 저장소에 commit하거나 외부에
배포하기 전에 프로젝트 책임자가 공개 범위를 검토해야 한다.

> [!CAUTION]
> - HyperNova가 현재 700만 원을 확보했다고 가정하지 않는다.
> - 현재 가용 현금은 PoC 용도의 300만 원이다.
> - 현재 외부 지원은 SOSLab사의 ML-X 120 Flash LiDAR 2대 무상대여뿐이다.
> - 홍보용 렌더를 최종 기체 형상이나 센서 배치로 해석하지 않는다.
> - 저장소에 ROS 2 package, URDF, firmware 또는 통합 baseline이 이미 있다고
>   가정하지 않는다.
> - 정량 요구사항은 팀 승인 없이 임의로 확정하지 않는다.

## 1. 정보 해석 규칙

### 1.1 상태 라벨

| 라벨 | 의미 |
| --- | --- |
| **CURRENT** | 기준일에 확인된 현재 사실 또는 적용 중인 저장소 결정 |
| **HISTORICAL** | 모집글 또는 이전 문서에 당시 계획으로 기록된 내용 |
| **TARGET** | 프로젝트가 지향하는 목표이며 아직 완료나 확보를 뜻하지 않는 내용 |
| **CANDIDATE** | 검토 중인 기술·구조·확장 아이디어 |
| **OPEN** | 선택, 수치, 책임 또는 계약이 아직 정해지지 않은 항목 |

### 1.2 출처 우선순위

1. 2026-08-14 사용자의 최신 명시적 정정
2. 같은 날짜의 사용자 프로젝트 브리프와 현재 상태 설명
3. 저장소에서 승인된 ADR과 저장소·안전·라이선스 정책
4. 2026년 8월 모집글과 당시 로드맵
5. 홍보용 콘셉트 이미지
6. 문서 작성 과정에서 도출한 해석

최신 정정은 관련 주제만 덮어쓴다. 예를 들어 모집글의 예산 정보는 역사적
맥락으로 남지만, 현재 확보액은 최신 사용자 정정을 따른다.

주제별 권한도 함께 적용한다. 미션, 역할, 현재 단계와 예산은 최신 사용자 설명이
기준이다. 저장소 구조, 기여 절차, 안전과 라이선스는 Accepted ADR과 저장소 정책이
기준이다. 대회 일정·주최·상금 같은 외부 사실은 공식 자료로 별도 확인한다.

### 1.3 개인정보 처리

이 문서에는 프로젝트 역할에 필요한 이름만 포함한다. 모집글에 있던 전화번호,
QR 코드, 지원 URL과 SNS 계정은 포함하지 않는다.

## 3. 프로젝트 목적

### 3.1 학생과 팀에 남길 가치

- HW, EE, SW, AI, CV 등 여러 전공이 실제 시스템 경계에서 협업한다.
- 참여자가 자신의 전공을 활용하면서 새로운 분야를 학습한다.
- 각 참여자에게 담당 기능, 실험 기록, 코드, 설계 또는 기술 문서가 남아야 한다.
- Notion과 GitHub를 이용한 요구사항 조율과 정기 설계 검토를 경험한다.
- 기구부터 전장, 제어, 인지, 자율화까지 연결되는 End-to-End 개발을 경험한다.

### 3.2 외부에 보여 줄 가치

- 회사와 학교가 이해하기 쉬운 명확한 운용 시나리오를 가진다.
- 기능 목록이 아니라 실제 환경에서 재현 가능한 통합 시연을 만든다.
- 대회 출전과 기술 검증을 통해 결과물의 완성도를 확인한다.

### 3.3 상위 성공 정의

HyperNova의 성공은 로봇이 주변을 인지하고, 주어진 임무를 수행한 뒤, 그 결과와
이상 정보를 사람에게 전달하는 전체 흐름을 목표 환경에서 재현하는 것이다.

## 4. 현재 운영 단계

2026-08-14 기준으로 1차 팀원 모집이 끝났다. 현재는 구현이나 대량 구매를
시작하는 단계가 아니라 다음 두 작업을 병행하는 전환 구간이다.

1. 신규 팀원을 위한 초반 온보딩·직무교육 방안 설계
2. 시스템 요구사항과 팀 간 개발 경계·인터페이스 정의

모집 당시 로드맵의 `프로젝트 정의·팀 빌딩`을 마무리하면서
`직무교육·상세설계` 진입을 준비하는 시점으로 본다.

### 4.1 현재 우선 산출물

- 메인 시나리오와 PoC 범위가 분리된 요구사항 baseline
- 각 요구사항의 검증 방법과 합격 기준
- 팀별 책임, reviewer, 의사결정 범위를 담은 책임표
- HW–EE–SW–AICV 사이 Interface Control Document 초안
- 팀별 교육 과제와 실제 프로젝트 산출물의 연결표
- PoC BOM, 지출 우선순위, 재사용 계획
- PoC 이후 단계로 넘어가기 위한 gate

## 5. 메인 운용 시나리오

### 5.1 해결하려는 문제

캠퍼스 시설점검은 사람이 넓은 공간을 반복 순찰해야 한다. 실내외, 계단,
경사로가 섞여 있어 단순 바퀴형 로봇만으로 모든 구간을 커버하기 어렵다.

HyperNova는 4족 이동 플랫폼이 지정된 순찰 임무를 수행하고, 이상 상황이
발생하면 위치와 현장 정보를 통제실에 전달하는 시스템을 목표로 한다.

## 6. 단계별 범위

| 단계 | 목표 | 범위 해석 |
| --- | --- | --- |
| PoC | 프로젝트의 완수 가능성 증명 | 다리 하나, 센서부, sim 내부 작동 정도 |
| 1차 | 자율 순찰과 이상 정보 전달 | 프로젝트의 우선 end-state이며 핵심 범위 |
| 2차 | 제한된 mobile manipulation | PoC·예산·일정 통과 후 진입하는 조건부 확장 |
| 3차 | 대상 인식과 Scout Drone/4 wheeled 로봇 연계 | 조건부 연구·확장 범위 |

### 6.1 1차 목표

- 기본 4족 locomotion
- 실내외, 계단과 경사 이동
- 카메라와 LiDAR 통합 3D SLAM
- 디지털 지도와 위치 추정
- waypoint 순찰 기능
- 이상 위치·이미지·알람 전송
- 음원 방향 추정과 추가 탐색

### 6.2 2차 목표

- 매니퓰레이터 추가
- 단순 형태의 문 열기
- 엘리베이터·자동문 등의 버튼 누르기
- 간단한 물체 조작
- 실제 시설 대신 축소 모형이나 제한된 시험 장치로 난이도 조절 가능

### 6.3 3차 목표

- 마이크 배열을 통한 이상상황 감지
- DB 기반 얼굴 또는 대상 인식
- 소형 드론 또는 바퀴형 Scout 연계
- 본체가 접근하기 어려운 영역의 추가 탐색

얼굴 인식은 개인정보, 데이터 보관, 접근 권한과 캠퍼스 촬영 승인을 먼저
검토해야 한다.

### 6.4 현재 비필수 응용 후보

- 실내 짐 운반과 Pick & Place
- 재난 현장 실내 구조 탐색
- 군용 정찰
- 응급키트 배송

이 항목들은 프로젝트의 확장 가능성을 설명하지만 현재 메인 시나리오와 동급의
확정 범위가 아니다.

## 7. 2027년 초 PoC

초기 PoC는 전체 1차 목표의 최종 통합 시연과 구분한다.

### 7.1 현재 자원과 목표

- 가용 현금 300만 원 안에서 구현해야 한다.
- 3D LiDAR 2대의 무상대여 지원은 확인됐다.
- 2027년 초 완성을 목표로 하며 정확한 deadline은 아직 정하지 않았다. 자금 조달을 위헤 최대한 빠른 완성이 좋다
- PoC 이후 최종 제작·통합을 위해 추가 모금이 필요하다.

### 7.2 모집 당시 제시된 방향

- 서브시스템 핵심 기술 검증
- Isaac Lab 기반 알고리즘 개발
- Teleoperation 기반 프로토타입
- 후속 후원·모금을 설명할 수 있는 시연

### 7.3 아직 정해야 할 PoC 계약

- PoC에 포함할 정확한 기능
- 시험 환경과 시연 시나리오
- 성공·실패를 가르는 정량 기준
- 구매 항목과 재사용 가능한 부품 - opendog v3 혹은 그 응용 프로젝트의 BoM을 기초로 둘듯
- 팀별 납품물과 통합 책임자
- 정확한 완료일과 review 일정

따라서 다른 프로젝트가 이 문서를 이어받더라도 `2027년 초 PoC`를 전체
자율 순찰 시스템 완성으로 임의 해석해서는 안 된다.

## 9. Scout 확장 구상

### 9.1 공유 LiDAR 구조

하나의 3D LiDAR를 장착한 Scout가 평소 4족 본체에 도킹되고, 도킹 상태에서는
본체의 센서로 동작한다. 추가 시야가 필요하면 LiDAR를 Scout에 둔 채 분리한다.

### 9.2 운용 후보

- 본체가 갈 수 있지만 위험한 구간을 Scout가 먼저 탐색
- 본체가 들어갈 수 없는 협소·붕괴·고소 영역을 Scout가 대신 탐색
- 본체 지도의 공백 영역을 추가 스캔으로 보완

### 9.3 형태 후보

- Drone: 접근 범위가 넓지만 payload, 비행시간과 제어 난도가 높다. Lidar은 미장착해야할수도
- Small rover: 구현이 쉽고 좁은 공간에 적합하지만 험지 성능이 제한된다.
- RGB-D/RGB Scout: LiDAR의 비용과 중량이 부담될 때 사용하는 경량 대안이다.

### 9.4 미결정 인터페이스

- 두 대의 LiDAR와 본체·Scout 사이 실제 할당
- docking 구조와 기계적 고정
- 전원, 충전과 통신
- 분리 전후 extrinsic calibration
- 지도 병합과 좌표계 관리
- 센서 소유권과 장애 시 동작

이 구조는 확정 baseline이 아니라 3차 확장 후보로 취급한다.

| System–HW–EE–SW–AICV | actuator torque·speed, encoder, control rate, 제동·역구동, fault 동작과 최종 선정 |
| HW–EE | mount, cable route, connector, 질량·열·전력 제한 |

| SW–AICV | ROS message/service/action, frame, 단위, timestamp, QoS, timeout |
| AICV–Simulation | observation, action, reward, termination, sim-to-real 가정 |

각 계약에는 owner, reviewer, version, 변경 승인 방법과 시험 방법이 필요하다.

### 11.2 아키텍처 원칙

- 조직도가 아니라 시스템 경계로 모듈을 나눈다.
- 인터페이스, 단위, 좌표계와 시간 기준을 구현보다 먼저 정한다.
- 재사용 가능한 core와 ROS 2·하드웨어 adapter를 분리한다.
- 실기와 시뮬레이션은 같은 robot description을 사용한다.
- 안전 정지, 상태 감시와 장애 동작은 모든 계층의 조건이다.
- 설정, calibration, 로그, commit과 hardware revision을 함께 식별한다.

## 12. 저장소 기준

저장소는 팀별 폴더가 아니라 기능·산출물 경계의 공개 monorepo다.

| 경로 | 책임 |
| --- | --- |
| `docs/` | 범위, 요구사항, 아키텍처, 개발·운용 지침, ADR |
| `description/` | URDF·Xacro, frame·joint, mesh, inertia, sensor pose |
| `firmware/` | MCU, motor controller, sensor interface와 안전 상태 |
| `ros_pkgs/` | 온보드 ROS 2와 운영자 관제 소프트웨어 |
| `sim_scenes/` | world, scenario, 시작 상태, 목표와 합격 기준 |
| `policies/` | 학습, 평가와 export 코드·설정 |
| `tools/` | 여러 영역이 공유하는 검증·변환 도구 |

배포 경계는 다음처럼 유지한다.

- board에서 실행되는 저수준 코드는 `firmware/`에 둔다.
- ROS 2 hardware adapter와 runtime node는 `ros_pkgs/`에 둔다.
- policy 학습·평가·export는 `policies/`에 두고 inference node·wrapper는
  `ros_pkgs/`에 둔다.
- simulator용 ROS 2 node·launch·adapter도 `ros_pkgs/`에 둔다.
- 기체 형상, frame과 joint는 `description/`을 단일 기준본으로 사용한다.

### 12.1 현재 성숙도

2026-08-14 기준 저장소는 README와 운영 문서 중심의 스캐폴드다. ROS 2 package,
URDF, firmware, simulation scene, policy와 통합 시험 baseline은 아직 없다.

유일하게 승인된 주요 ADR은 기능·산출물 기준 monorepo로 시작한다는 결정이다.
시스템 아키텍처, ROS 2 배포판, OS, simulator와 하드웨어 baseline은 미정이다.
