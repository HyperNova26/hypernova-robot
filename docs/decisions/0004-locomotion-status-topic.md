# ADR-0004: 로봇 상태 토픽과 상태 코드

- 상태: **Proposed**
- 제안: 2026-11-15
- 관련: 로드맵 G-006, S-005(`/localization/status`), [로봇 상태 토픽 인터페이스](../interfaces/locomotion-status.md)

## 배경

로봇이 지금 서 있는지, 걷는지, 넘어졌는지를 SW팀 앱이 알아야 표시하거나 대처할 수 있습니다(G-006). 구현은 `ros_pkgs/hn_robot_state/`에 있고, 시뮬레이터 세 곳(MuJoCo, Isaac Sim, Isaac Lab)에서 정지·보행·낙상이 올바른 상태로 나오는지 확인했습니다. 실기에서 같은 입력을 만들어 넣는 노드는 아직 없습니다.

앱은 토픽 이름, QoS, 상태 번호, 이유 문자열에 의존하게 됩니다. 한 번 앱이 번호로 분기하면 번호를 바꾸는 일이 조용한 오동작이 되므로, 구현 파일이 아니라 팀이 함께 보는 곳에 정해 두어야 합니다. 대시보드 쪽 선례인 S-005의 `/localization/status`가 숫자 enum 방식이라 같은 방식을 따르는 것이 자연스럽습니다.

## 검토한 선택지

**A. 인터페이스 문서에만 적기** — 가장 빠릅니다. 대신 번호가 구현 변경과 함께 조용히 바뀔 수 있고, 바꾸는 사람이 앱 쪽 영향을 확인할 계기가 없습니다.

**B. 상태 이름 문자열만 약속하기** — 사람이 읽기 좋습니다. 하지만 앱이 문자열 비교로 분기하게 되고, S-005의 숫자 enum 방식과 달라 대시보드에서 두 상태 토픽을 같은 방식으로 다룰 수 없습니다.

**C. 숫자 코드, 이름, 이유를 함께 싣고 번호를 고정하기** — S-005와 같은 방식입니다. 번호가 계약이고 이름과 이유는 사람이 읽는 보조 정보입니다. 번호를 고정해야 하므로 새 상태를 넣을 때 이 문서를 거쳐야 합니다.

메시지 타입은 별도 질문입니다. S-005가 쓰는 `hn_interfaces`는 2026-11-15에 조직 저장소 코드, 원격 브랜치, 컨테이너, 이 PC에서 찾지 못했고 위치와 소유자를 확인하지 못했습니다. 그래서 표준 `diagnostic_msgs/DiagnosticArray`로 시작했습니다. 커스텀 메시지로 바꾸는 코드는 몇 줄이지만, 패키지 작성, `hn:sim`에서의 빌드(기본 `VIRTUAL_ENV` 때문에 `colcon build`가 empy를 찾지 못함), 모든 구독 쪽 빌드 배포, 구독자 타입 변경 조율이 비용입니다. 받는 쪽에 인터페이스 패키지가 없으면 `ros2 topic echo`와 `foxglove_bridge`가 그 채널을 쓰지 못하는 것도 확인했습니다. 구독자가 생기기 전에 바꾸는 편이 쌉니다.

## 결정

C로 가고, 아래를 제안합니다. 합의 전까지는 `Proposed`입니다.

### 1. 토픽

| 항목 | 값 |
| --- | --- |
| 이름 | `/locomotion/status` |
| 타입 | `diagnostic_msgs/msg/DiagnosticArray`, `status`는 항상 1개(임시, [다시 볼 조건](#다시-볼-조건) 참고) |
| QoS | reliable, transient_local, KEEP_LAST, depth 1 |
| 발행 | 상태가 바뀌면 즉시, 그 밖에는 10 Hz heartbeat |
| `header.stamp` | 시스템 시간(`time.time_ns()`). 시뮬레이션 시간은 `values`의 `sim_t` |

### 2. 상태 코드

| code | 이름 | `level` | `reason` |
| --- | --- | --- | --- |
| 0 | `INITIALIZING` | OK (0) | `calibrating` |
| 1 | `STANDING` | OK (0) | `idle` |
| 2 | `WALKING` | OK (0) | `moving` |
| 3 | `TILTING` | - | 예약, 아직 내보내지 않음 |
| 4 | `SLIPPING` | - | 예약, 아직 내보내지 않음 |
| 5 | `FALLEN` | ERROR (2) | `tilt`, `off_ground`, `low_height` |
| 6 | `STALE_INPUT` | STALE (3) | `no_input` |

- 판정 조건, 임계값, `values` 필드와 단위는 [인터페이스 문서](../interfaces/locomotion-status.md)가 정합니다. 번호, 이름, `level`, `reason` 문자열만 이 ADR이 정합니다.
- 번호는 한 번 정하면 바꾸거나 다른 뜻으로 재사용하지 않습니다. 3과 4는 번호만 잡아 둔 것이며, 내보내기 시작할 때 `level`과 `reason`을 정해 이 표를 갱신합니다(`level`의 WARN은 이때 쓸 자리입니다).
- 새 상태나 새 `reason`은 이 표에 먼저 추가합니다. 구독하는 쪽은 모르는 `code`를 받으면 오류로 보지 않고 `level`만 따라 처리하는 것을 제안합니다.
- `STALE_INPUT`은 판정기가 입력을 못 받는 상태이지 로봇의 상태가 아닙니다. 발행 쪽 heartbeat가 낸다는 점을 앱이 알아야 합니다.
- `FALLEN`은 로봇이 스스로 일어나면 풀립니다. 앱이 유지 시간으로 낙상을 판단하지 않고 해제 이벤트를 함께 봐야 합니다.

## 결과

- 앱은 `code`(정수)로 분기하고 `state`와 `reason`은 표시용으로 씁니다.
- 번호가 계약이 되므로 판정 코드를 고치는 사람은 번호를 못 바꿉니다. 상태를 늘리려면 이 ADR을 거쳐야 해서 변경이 한 단계 느려집니다.
- 표준 메시지로 시작했기 때문에 지금 구독자가 쓰는 타입은 임시입니다. 타입을 바꾸면 모든 구독자를 같이 바꿔야 합니다.
- 이 표는 시뮬레이터에서만 확인했습니다. 임계값은 시뮬레이션 로그로 맞춘 초기값이고 실기 IMU 노이즈와 모터 지연은 반영되지 않았습니다. 낙상 지연(고장 시작부터 `FALLEN`까지)은 판정기 몫 0.20 s에 로봇이 실제로 쓰러지는 시간이 더해진 값이어서, 앱이 기대하는 응답 시간은 실기에서 다시 재야 합니다.
- Isaac Sim의 정상 보행 기울기가 최대 46.9°에서 48.5°(70° 기준까지 21.5°에서 23° 여유)라서, `TILTING`을 넣을 때 기준을 정하려면 시뮬레이터별 여유를 먼저 봐야 합니다.

## 다시 볼 조건

- `hn_interfaces`의 위치와 소유자가 확인되어 커스텀 메시지로 옮길 때(S-005와 같은 패키지를 쓸지 포함). 이때 이 ADR의 타입 항목을 갱신하거나 새 ADR로 `Superseded` 처리합니다.
- SW팀 앱의 수신 경로가 S-005의 `foxglove_bridge`(WebSocket)가 아닐 때. QoS나 타입 선택이 달라질 수 있습니다.
- `TILTING`이나 `SLIPPING`을 내보내기 시작할 때.
- 실기에서 입력을 만드는 노드가 생기고 임계값을 실기 데이터로 다시 맞출 때.
- S-005의 `/localization/status` 코드 방식이 바뀔 때.
- SW팀이 상태 코드 표에 동의하면 `Accepted`로 바꿉니다. 그 전에는 바꾸지 않습니다.
