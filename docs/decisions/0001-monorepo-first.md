# ADR-0001: 단일 저장소로 시작

- 상태: **Accepted**
- 제안: 2026-08-01
- 승인: 2026-08-02

## 배경

기구, 전자, 소프트웨어, 인지로 나뉘어 협업하는데 시스템 인터페이스와 릴리스 경계는 아직 없습니다. 이 상태에서 팀별 저장소부터 만들면 통합 변경 하나가 저장소 여러 개에 걸치고, 문서와 설정을 어디에 둘지 매번 애매해집니다.

TurtleBot3, Barkour, RoboJackets URC 같은 공개 프로젝트를 찾아봤습니다. 기체 하나를 개발하는 초기에는 팀 이름이 아니라 기능과 산출물로 나눈 단일 저장소가 대부분이었습니다. 팀별로 쪼갠 사례는 거의 없었고, 있더라도 설계가 끝난 뒤 공개용으로 떼어낸 경우였습니다.

## 검토한 선택지

**A. 팀별 저장소** — 권한은 단순합니다. 대신 인터페이스 변경, 통합 시험, 버전 조합 관리가 금방 복잡해집니다. 지금은 각 저장소를 따로 릴리스할 이유도 없습니다.

**B. 단일 저장소 + 팀별 폴더** — 저장소 수는 줄지만 조직이 바뀔 때마다 파일 구조가 따라 바뀝니다. 기능 하나가 여러 팀 폴더로 흩어지는 것도 문제입니다.

**C. 단일 저장소 + 기능·산출물 경계** — `description/`, `firmware/`, `ros_pkgs/`, `sim_scenes/`, `policies/`, `docs/`, `tools/`로 나누고, 세부 package는 실제로 구현할 때 기능별로 추가합니다.

## 결정

C로 갑니다. 팀장이 해당 영역 리뷰를 맡는 건 그대로지만, 파일 위치는 팀 이름이 아니라 기능과 산출물, 인터페이스로 정합니다.

Fusion·KiCad 원본과 부품 선정 기록은 각 협업 도구와 Notion을 기준본으로 씁니다. 저장소에는 실기와 시뮬레이션이 직접 읽는 description 산출물만 둡니다. 외부 Git 저장소를 작업 트리에 넣어야 할 때는 사본을 만들지 말고 submodule로 commit을 고정합니다.

## 결과

- 한 PR에서 인터페이스, 구현, 설정, 문서를 같이 볼 수 있습니다.
- 모든 팀이 같은 기체 revision과 통합 상태를 기준으로 작업합니다.
- 같은 description과 simulation scene을 여러 영역이 중복 없이 씁니다.
- 대신 저장소가 커지면 clone과 권한 분리가 불편해질 수 있습니다.

## 다시 볼 조건

- 어떤 영역에 독립적인 버전과 릴리스 주기가 필요해질 때
- 접근 권한이나 보안 경계를 나눠야 할 때
- 대용량 CAD·데이터로 clone과 CI 비용이 눈에 띄게 늘어날 때
- 외부에서 독립 패키지로 가져다 쓸 때
