# ADR-0001: 단일 저장소로 시작

- 상태: **Proposed**
- 날짜: 2026-08-01

## 배경

기구, 전자, 소프트웨어, 인지로 나뉘어 협업하지만 시스템 인터페이스와 릴리스 경계가 아직 없습니다. 이 상태에서 팀별 저장소를 먼저 만들면 통합 변경 하나가 여러 저장소에 걸치고, 문서와 설정을 어디에 둘지 매번 애매해집니다.

TurtleBot3, Barkour, RoboJackets URC처럼 공개된 로봇 프로젝트를 봐도, 한 기체를 개발하는 초기에는 팀 이름이 아니라 기능과 산출물로 나눈 단일 저장소가 많았습니다. 팀별로 저장소를 나눈 사례는 거의 없었고, 나눈 곳은 설계가 끝난 뒤 공개용으로 분리한 경우였습니다.

## 검토한 선택지

**A. 팀별 저장소** — 권한은 단순하지만 인터페이스 변경, 통합 시험, 버전 조합 관리가 빨리 복잡해집니다. 지금은 각 저장소를 따로 릴리스할 이유가 없습니다.

**B. 단일 저장소 + 팀별 폴더** — 저장소 수는 줄지만 조직이 바뀔 때마다 파일 구조가 바뀌고, 기능 하나가 여러 팀 폴더로 흩어집니다.

**C. 단일 저장소 + 시스템·산출물 경계** — `hardware/`, `firmware/`, `software/`, `simulation/`, `docs/`로 나누고, 소프트웨어는 실제 구현할 때 기능별 패키지로 나눕니다.

## 결정

선택지 C를 씁니다. 팀장이 해당 영역 리뷰를 맡을 수는 있지만, 파일 위치는 팀 이름이 아니라 산출물과 인터페이스로 정합니다.

## 결과

- 한 PR에서 인터페이스, 구현, 설정, 문서를 같이 볼 수 있습니다.
- 모든 팀이 같은 기체 revision과 통합 상태를 기준으로 작업합니다.
- 대신 저장소가 커지면 clone과 권한 분리가 불편해질 수 있습니다.

## 다시 볼 조건

- 어떤 영역에 독립적인 버전과 릴리스 주기가 필요해질 때
- 접근 권한이나 보안 경계를 나눠야 할 때
- 대용량 CAD·데이터로 clone과 CI 비용이 눈에 띄게 늘어날 때
- 외부에서 독립 패키지로 가져다 쓸 때
